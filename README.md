# Транскрибация звонков техподдержки → саммари → 1С

Локальный сервис, который превращает записи телефонных звонков в текст с таймкодами, оценивает эмоции
по голосу и строит карточку звонка для руководителя: тема, суть, итог, следующий шаг, приоритет,
оценка негатива и риски. Всё работает **локально, без облачных API** (152-ФЗ): распознавание, эмоции
и LLM крутятся на своём сервере.

## Что получается на выходе

Для каждого звонка:

- **Транскрипт** по фразам с таймкодами; для стерео-записей — по ролям «Клиент / Оператор».
- **Эмоции по голосу** для каждой фразы (злость / грусть / нейтрально / позитив) и сводка по звонку.
- **Карточка звонка**: тема, клиент, суть обращения, итог, следующий шаг, пересказ из 3–5 предложений,
  ключевые детали (сроки, суммы, номера ошибок, программы и оборудование).
- **Оценка**: приоритет (обычный / важный / критический), негатив 0–10, тон, риски — каждый вывод
  подкреплён дословной цитатой клиента.

## Как устроено

```
аудио (wav/mp3/ogg/m4a)
  └─ ffmpeg → 16 кГц, по каналам
      └─ silero-vad: нарезка по паузам на фрагменты до 20 с
          └─ GigaAM-v3 e2e RNNT: распознавание с пунктуацией (пакетами)
              ├─ автозамены терминов (ФСРАР, ЕГАИС, АТОЛ, 1С…)
              ├─ GigaAM-Emo: эмоция каждой фразы
              └─ саммари (GigaChat 3.1 Lightning через Ollama):
                   1. LLM: факты + сигналы «да/нет» с дословными цитатами
                   2. код: проверка цитат по расшифровке → оценка правилами
                   3. LLM: карточка звонка по фактам
```

**Распознавание.** GigaAM принимает фрагменты не длиннее 25 с, а штатный режим для длинных записей
требует pyannote и токен Hugging Face. Вместо него — своя нарезка silero-vad и пакетная подача фрагментов
в модель; параметры VAD подобраны на реальных записях АТС (тихая речь второй стороны сохраняется,
музыка ожидания и разговоры в офисе в текст не попадают).

**Саммари — цепочка, а не один промпт.** Маленькая локальная модель теряет конкретику, когда за один
запрос делает всё сразу. Поэтому:
- первый шаг только извлекает факты и отвечает «да/нет» на вопросы о клиенте (претензия к сервису,
  угроза, повторное обращение, работа стоит, торопит, благодарит), и каждое «да» — с цитатой;
- код проверяет, что цитата действительно есть в расшифровке, отбрасывает выдуманные, ищет угрозы
  по ключевым словам и по прозрачным правилам считает негатив, приоритет, тон и риски;
- второй шаг пишет карточку строго по фактам; длину и формат держит JSON-схема (грамматика Ollama),
  код убирает повторы и обрывки разметки.

Промпты — в [`transcriber/app/prompts.py`](transcriber/app/prompts.py), правила оценки —
в [`transcriber/app/summary.py`](transcriber/app/summary.py).

## Качество

Саммари оценивается скриптом [`eval_summary.py`](transcriber/scripts/eval_summary.py) по эталону:
для каждого звонка — список ключевых фактов, которые обязаны попасть в текст, ожидаемые тон, приоритет
и диапазон негатива. На 15 реальных звонках (эталон и записи в репозиторий не входят):

| Метрика | Один промпт | Цепочка |
|---|---|---|
| Ключевые факты в саммари | 71% | **86%** |
| Тон | 15/15 | 14/15 |
| Приоритет | — | **14/15** |
| Негатив в допустимом диапазоне | — | **13/15** |
| Длина 3–5 предложений | 12/15 | **15/15** |
| Тема ≤ 7 слов | 10/15 | **15/15** |
| Куски промпта в ответе | 8 | **0** |

**Скорость** на CPU (Intel i3-12100, 4 ядра, без GPU): распознавание ~5 с на минуту аудио,
с эмоциями ~10 с; саммари ~2 мин на звонок (модель не помещается в RAM целиком).
На сервере с достаточной памятью или GPU — быстрее.

## API

| Метод | Описание |
|---|---|
| `POST /jobs` | multipart: `file`, `call_id` (обяз.), `phone`, `ext`, `call_date` → `{call_id, status}`. Повтор с тем же `call_id` перезапускает задачу без дубля |
| `GET /jobs/{call_id}` | `status`, `duration_s`, `phrases[]` (канал, мс, текст, эмоция), `text`, `emotion`, `summary` |
| `GET /health` | готовность моделей, ffmpeg, LLM, очередь, расписание загрузки с АТС, уборка |
| `POST /ats/fetch` | скачать записи с АТС сейчас: `day`, `days`, `limit`, `dry_run` |

Очередь задач в SQLite переживает перезапуск, есть папка автоприёма (`INBOX_DIR`), basic-auth.
Если LLM недоступна или ответила мусором, задача не падает — отдаётся транскрипт без саммари.

## Установка на сервер (Docker)

Пошаговая инструкция с проверкой всей цепочки — **[INSTALL.md](INSTALL.md)**; для Windows Server без Docker —
**[INSTALL_WINDOWS.md](INSTALL_WINDOWS.md)** (установщик `deploy\windows\install.ps1` ставит Python, модели, Ollama
и две службы Windows; управление — `deploy\windows\ct.ps1`). Коротко про Docker:

Нужны Docker с Compose v2, ~30 ГБ диска, 16 ГБ RAM (LLM занимает ~7 ГБ). Два контейнера: сервис
транскрибации и Ollama с LLM; при первом запуске модели скачиваются сами (GigaAM ~1 ГБ, GigaChat 6.5 ГБ).

```bash
git clone https://github.com/qqsinka/call-transcriber.git && cd call-transcriber
cp .env.example .env        # обязательно сменить AUTH_PASSWORD
make docker-up              # или: docker compose up -d --build
make docker-logs            # дождаться загрузки моделей
make docker-status          # /health -> "status": "ok"
python3 transcriber/scripts/checks/smoke_api.py samples/call_mono.mp3 --password <пароль из .env>
```

- API — `http://сервер:8000`, LLM наружу не публикуется.
- `./data` — очередь задач (`jobs.db`) и словарь автозамен `replacements.txt` (правится на лету);
  `./inbox` — папка автоприёма: положенная туда запись обрабатывается и переезжает в `inbox/done`.
- Перезапуск после сбоя и ротация логов настроены; обновление — `git pull && make docker-up`.
- **GPU (NVIDIA):** `make docker-up-gpu` — распознавание и LLM на видеокарте (нужен NVIDIA Container Toolkit).
- **Сервер без интернета:** на машине с интернетом `make docker-up` (скачает LLM), затем `make docker-export` —
  получатся `call-transcriber-images.tar.gz` (образы, веса GigaAM внутри) и `ollama-models.tar.gz` (LLM).
  На сервере: `docker load < call-transcriber-images.tar.gz`, распаковать LLM в том
  `call-transcriber_ollama`, `docker compose up -d --no-build`.
- Внешний Ollama вместо контейнера: `DOCKER_LLM_URL=http://адрес:11434` в `.env`.
- **Ночной режим:** если АТС отдаёт записи веб-списком (`<адрес>/ГГ/ММ/ДД/<линия>/*.mp3`, basic-auth),
  сервис в `ATS_FETCH_AT` (например, 20:30) сам забирает записи за день, обрабатывает их до утра
  и удаляет аудио после успешной обработки (текст и саммари остаются в базе). Пустышки и уже
  обработанные звонки не качаются; дата, номер абонента и линия берутся из имени файла.
  Вручную: `make docker-fetch-ats DATE=2026-10-26 LIMIT=2` или `POST /ats/fetch?day=…&limit=…`.
- **Реальное время:** линии из `ATS_LIVE_LINES` проверяются каждые 2 минуты в рабочие часы — звонок
  обрабатывается через несколько минут после окончания; ночной режим добирает пропущенное.

## Локальный запуск (без Docker)

Linux / WSL2, Python 3.10+, ffmpeg, [Ollama](https://ollama.com) с моделью:

```bash
ollama pull hf.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF:Q4_K_M
cp .env.example .env        # адрес LLM, логин/пароль, параметры VAD
make install                # CPU; для GPU: make install TORCH_INDEX=https://download.pytorch.org/whl/cu126
make run                    # http://localhost:8000
make test
```

Пакетная обработка папки (транскрипт + эмоции, затем саммари):

```bash
python transcriber/scripts/run_real.py <записи> <транскрипты> --txt-only --emotion-dir <эмоции>
python transcriber/scripts/summarize_dir.py <транскрипты> <саммари> --emotion-dir <эмоции>
```

## Структура

```
transcriber/app/        сервис: audio, asr, emotion, summary, prompts, replacements, db, worker, main
transcriber/scripts/    пакетная обработка, генерация тестовых записей, оценка качества, сквозная проверка
transcriber/tests/      юнит-тесты (pytest)
samples/                синтетические тестовые записи (TTS) и публичный пример GigaAM
```
